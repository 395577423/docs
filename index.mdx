## 1 接口规则
### 1.1 协议规定

| 术语 | 描述 |
| --- | --- |
| 传输方式 | 为保证交易安全性，建议采用 HTTPS 传输 |
| 提交方式 | 采用 POST 方法提交 |
| 数据格式 | 提交和返回数据都为 json 格式 |
| 字符编码 | 统一采用 UTF-8 字符编码 |
| 签名算法 | HMAC-SHA1 |
| 签名要求 | 请求和接收数据均需要校验签名，详细方法请参考签名算法 |
| 判断逻辑 | 先判断协议字段返回，再判断业务返回，最后判断交易状态 |

### 1.2 签名算法
目前采用HMAC-SHA1签名算法，为了方便比较，签名结果统一转换为小写字符。
签名串一共有七行，每一行为一个参数。行尾以 \n（换行符，ASCII编码值为0x0A）结束，包括最后一行。如果参数本身以\n结束，也需要附加一个\n。
#### 签名字拼接符串  =  HTTP请求方法\n  + URL\n  +  Client-Id\n  +  Signature-Type\n + Timestamp\n+ Nonce-Str\n + 请求报文主体\n
#### 签名拼接字符串参数说明：
HTTP请求方法：HTTP请求的方法（GET,POST,PUT）等。
#### URL：假设请求接口地址为“https://xhj-sit.91xft.cn/mch/pre/register“，则URL的值为“/mch/pre/register”。
Client-Id：我们分配提供。
Signature-Type：固定值，HMAC-SHA1。
请求时间戳：当前时间的时间戳，13位数字。
请求随机串：随机字符串。
请求报文主体：请求报文体内容。
Signature = HmacSHA1( 签名字拼接符串，秘钥EKY).toLowerCase。
其中的秘钥EKY由我们分配提供。
得到Signature值后同Client-Id、Nonce-Str、Timestamp放入请求头headers中。
#### 注意：我们接口的响应签名算法中，去掉了HTTP请求方法和URL两个参数，即：
响应签名字拼接符串  =    Client-Id\n  +  Signature-Type\n + Timestamp\n + Nonce-Str\n + 请求报文主体\n
### 1.3 响应报文说明
所有接口先判断HTTP状态码，状态码非200的，可以认为是失败，失败的请求，可以通过响应body里面的code和message查看具体失败原因。
示例：

```json
{
  "code": "20001",
  "message": "签名验证失败"
}
```

状态码为200的请求，表示请求成功，根据接口文档中各个接口响应参数说明做对应处理。
### 1.4 报文体加密规则说明
针对正常的请求和响应报文，做了国密算法SM4加密，双方约定好密钥。
特别注意的一点是，响应只有状态码为200时，报文体才做加密，否则直接展示错误码code和错误描述message。
加解密java代码样例(jdk要求>=1.8)：

```java
import org.junit.Assert;import org.junit.Test;import com.hrfh.crypto.HrCrypto;public class HrCryptoTest {    @Test    public void sm4() throws Exception {        final String plainText = "这是明文1";//        final String secretKey = "0123456789ABCDEF";// 密钥         HrCrypto crypto = HrCrypto.sm4(secretKey);// 获取加解密处理器        // 明文加密        String encodedString = crypto.encode(plainText);        System.out.println("加密后数据[" + encodedString + "]");        // 密文解密        String plainText2 = crypto.decode(encodedString);        System.out.println("解密后数据[" + plainText2 + "]");        // 比较前后结果        Assert.assertEquals("解密后与原文不一致", plainText, plainText2);        System.err.println("加解密测试完成");    }}
```

### 8.3 打款验证申请回执
#### 说明：由于打款是通过⼈⾏通道，可能出现退汇的场景，即先返回打款成功的消息，后返回打款失败的消息。
在⽹络异常或商户系统故障恢复后的情况下，可能会出现发送回执消息乱序的情况，因此不可以假设打款成
功的消息和打款失败的消息谁先到谁后到。商户需要正确兼容处理。
建议的处理措施是，针对相同verifyId的多笔回执消息，打款失败的消息可以覆盖打款成功的消息，但
是打款成功的消息不能覆盖打款失败的消息。
